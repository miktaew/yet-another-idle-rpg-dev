# Translation handbook

How player-facing text works in this game, and the rules for translating it.

Turkish counterpart: [I18N.TR.md](I18N.TR.md).

---

## 1. How it works

Player-facing text is never written in `src/`. Dialogue **structure** lives in
`src/dialogues.js`; the **text** those nodes display lives in
`locales/<language>.js` behind a string id.

- `src/translation.js` holds `translationManager`. `init(language)` loads that
  locale and, for any language other than the default, also loads the default so
  there is something to fall back to. `getText(language, id)` resolves one id.
- The locale object is a **flat, single namespace**. It is assembled from sections
  at the bottom of the file (`{...racial, ...ui, ...stats, ...skills, ...bio}`) and
  exported as the default. The sections are for the reader's benefit only.
- `translateUI(language)` fills every element carrying a `data-translation`
  attribute. Everything else goes through `getText` when its panel is drawn.
- A missing id falls back to the default language and logs a warning once. So a
  partial locale is safe: untranslated text shows in English rather than as a
  placeholder.
- `npm run check` prints the reference key count and each locale's coverage.
  Unknown keys are an error; missing keys are a warning. `LOCALE_STRICT=1` makes
  missing keys fatal.

### Racial text variants

An id prefixed with `mofu#` is the variant shown when the beastkin flag is set.
Resolution happens **per language**: a language that has the base text but no
variant answers with its own base text rather than borrowing the other language's
variant, because staying in the active language matters more than getting the
variant. A `mofu#` key with no base key can never be reached, and `npm run check`
treats it as an error.

### Adding a language

1. Create `locales/<name>.js` exporting a default flat object.
2. Register it in `languages` in `src/main.js`, and give it a display name in
   `language_names` — each language names itself in its own language.
3. That is all. The selector in the options panel is built from `languages`, and
   the choice is already saved and restored with the rest of the save data.

The selector switches live. `translateUI` updates the static chrome immediately;
dialogue, tooltips and quest text update as their panels are redrawn. **A newly
added locale file is invisible in bundle mode until the next build** — esbuild
globs `locales/` at build time. Dev mode fetches it at runtime.

## 2. Hard rules

### Never translate a key

Keys are simultaneously lookup ids and, for content registries, **save data**.
Translating a key is the same operation as renaming it, and renaming one silently
breaks existing saves. Only values are translated.

This is why the `skills` section maps skill ids to shown names: the key
`"Shield blocking"` stays exactly as it is, and only the value changes.

### Translate meaning and tone, not words

The result must read as though it had been written in the target language. Rewrite
sentence structure freely — English word order, punctuation habits and paragraph
rhythm are not binding. What must survive is the meaning and the register.

Not acceptable: machine-translation phrasing, calques, idiom translated
word-for-word, or the wrong sense of a word that has several.

> "Spider web" is a **web of silk**, not a computer network. Resolve the sense
> against the in-game context before choosing a word.

### Translate in context units

A string is read on screen underneath whatever is above it. The unit of
translation is therefore the screen region, never the individual string:

- a player question **together with** the reply that answers it;
- a stat's short form **together with** its long form — the tooltip has to name
  the same thing the row abbreviates;
- a dialogue's description **together with** the lines it introduces;
- a label **together with** the values that can appear after it (`"Height"` +
  `"Short"` must read as one line).

Nothing below may contradict or drift from what is above it.

### Keep the voice

Read [STORY.md](STORY.md) section 4 before translating narrative text. The register
is wry-cozy over a grim substrate: comedy carries the weight, the horror is ambient.
A translation that is accurate but flat has failed.

Stage directions are written `*[like this]*` and that convention is kept in every
language.

### Improve only where the original is merely terse

Where English left an abbreviation unexpanded and the long form adds nothing
(`"EP"` for both forms), spelling it out in the target language is right — it is
clearer and still faithful. Do not use this as licence to add information the
original does not carry.

## 3. Turkish specifics

### Address register

Mixed, per NPC. The map is in [STORY.md](STORY.md) section 6. It is an authoring
convention, not an engine feature: each line is a separate id, so the register is
written into the line. Do not try to make it runtime-selectable.

### Dotted and dotless i

`toUpperCase()` and `toLowerCase()` are not locale-aware in this codebase, and
Turkish `ı`/`i` do not map the way the default locale assumes. Concretely: the
capital of `ırk` is `Irk`, not `İrk`. Where the game capitalises a translated
string itself — `capitalize_first_letter` in `src/misc.js` — check the result for
any word starting with `ı` or `i`.

### Sentences assembled from fragments

Turkish is agglutinative and its word order differs, so a sentence built by
concatenating an English fragment with a name cannot be translated correctly. Where
that happens the fragment has to become a parameterised template before it can be
localised. Report these rather than working around them.

### Plurals

Turkish does not pluralise a noun that follows a number. "3 items" is
"3 eşya", not "3 eşyalar". Where the English text does naive `s`-suffixing or
`item(s)`, the Turkish form usually needs no marker at all.

### Never put a suffix on a slot

Some texts carry `{slot}` placeholders, filled at runtime with another locale row.
They are what covers the 203 items the game generates rather than declares — a
blade is "iron" plus "short blade", assembled from `pattern component name`.

A slot's value is **not known** when you write the text, so nothing may be attached
to it. In English that is barely a constraint. In Turkish it is the whole problem:

- The ablative is `-dan`, `-den`, `-tan` or `-ten`, chosen from the last vowel and
  the last consonant of the word it attaches to. `demirden`, `çelikten`, `ketenden`,
  `ahşaptan`. `{material}dan` is wrong for most values it will ever receive.
- The same goes for the accusative, the dative, the possessive and the plural.

So the text has to be built so the slot stays bare. Instead of
`{material}dan yapılmış kısa bir bıçak`, write
`{material} kullanılarak yapılmış kısa bir bıçak` — `kullanılarak` takes the
grammar and the slot stays a plain noun. `npm test` asserts this for the component
descriptions; if you reword one into taking a suffix, it fails.

The second effect is subtler. A slot value has to fit the pattern it lands in, and
that reaches back into the words you choose. English assembles the material
`iron chainmail` with the piece word `armor` into `Iron chainmail armor`. The
Turkish for chainmail is `zincir zırh`, which already contains the piece word, so
using it as the material's name form would produce `Demir zincir zırh zırh`. The
name form is therefore `demir zincir` and the description form is
`demir zincir zırh` — the two are separate rows for exactly this reason.

### A number in a slot is the same trap, twice over

The skill effect readouts fill their slots with numbers computed at render time.
Two things follow, and both were got wrong in the first draft:

- **Turkish writes the percent sign before the number.** `%1.23`, never `1.23%`.
- **A number cannot take a suffix**, and not merely because the slot is unknown:
  the suffix depends on how the number is *read aloud*. `7'sini` (yedisini) but
  `10'unu` (onunu); `x2'ye` but `x1.5'e`. No single form is right for every value
  the slot will receive. Reword so the suffix lands on a following word -
  `%{v3} kadarını`, `x{v1} seviyesine` - and the slot stays a bare numeral.

The decimal separator is left as the dot the code produces. Turkish would use a
comma, but that is a formatting job for the code, not something a locale row can
fix, and the game shows dots everywhere else.

### Two forms of the same material

`material <key>` is what a description says an item is made of. `material name <key>`
is what goes into its name. They are usually identical; they differ for five
materials, because those declare a display name in the generator — `rough wood`
shows as `simple wooden`.

Do not merge them. The name form feeds the assembled name, and the assembled
**English** name has to equal the item's registry key, which is written into save
files. A wrong name form does not mistranslate an item, it renames it.

### Word order lives in the pattern

`pattern component name` is `{material} {type}` in both languages, because a
Turkish material name works as an attributive with no suffix and the order happens
to match. That is a coincidence, not the design. A language that needs the other
order changes its own pattern row and touches nothing else — never reorder by
editing the parts.

### Races and proper nouns

Race names that are Japanese loanwords stay as they are: **Nekomimi**,
**Inumimi**, **Nezumimi**, **Kitsunemimi**. Their alternative names translate
(`Cat person` → `Kedi insan`). `Lizardkin` becomes `Kertenkele soylu`.

Per [STORY.md](STORY.md) section 5, proper nouns are reserved for peoples, places,
materials and the mythic. Those are **not** translated — Snake Fang Tribe, Carya
Canyon, Atratan, Ratzor Rathai keep their form. Descriptive names are translated.

### The swamplands

The Snake Fang camp has its own vocabulary, and the whole cast has to agree on it,
or trees written days apart end up contradicting each other from one hut to the next.

`obaru`, `kazoku`, `sosso`, `zalgo`, `menaka` and `tumana` are the cook's own words
and are never translated. He glosses them himself, in his own branches, so a locale
that pre-empts him takes the scene away from him.

**A trap in Turkish.** "To sharpen" is `bilemek`, and its present continuous —
`bile-` plus `-iyor` — collapses to `biliyor`, which is the verb *to know*. In a
dialogue tree whose entire subject is knowing the tribe, that is not a near miss.
Use any other form: `bilemek`, `bilenir`, `bileyip`. Never the `-iyor` one.

Counting is a register marker, not sloppiness. The tanner says `beş düzine`, the
cook `üç kere yirmi`, and the hero plain `60`. All three mean the same number, and
the difference is the characterisation.

## 5. Known gaps

There is no longer any player-facing English left in the game. What follows is
what a translator should know about the parts that are structurally awkward, not a
backlog.

- **Two loading-screen messages stay English on purpose**, and the reason changed:
  it is no longer that no locale is loaded. `src/translation.js` imports the locales
  statically, so a lookup works from the program's first line. The first message
  renders before the save has been read, so `language` still holds the default and a
  translated string there would be the wrong language rather than no language; the
  second is kept as deliberately untranslated flavour. Both are marked in
  `src/main.js`. The third one, "Waiting for you to click 'PLAY'", used to be
  unmarked English for no reason and is now translated.
- **`help.html` and `changelog.html` are standalone pages** opened in a new tab, so
  they cannot go through the translation layer. Each language gets its own file -
  `help.tr.html`, `changelog.tr.html` - and the buttons are relinked when the
  language changes. A language with no translated page keeps the English one, so
  adding a third language does not break either button. The cost is that the pages
  drift: an entry added to `changelog.html` has to be added to every translation
  by hand.
- **A reward amount is duplicated in prose.** `sup fight answ` states "4 silver
  coins" while the payout lives in `src/dialogues.js` as `money: 4000`, so every
  locale carries the number by hand.
- **A player-side line that is only a stage direction has no addressee**, so a
  formal register cannot be shown there. All three of the old woman's player-side
  ids are stage directions, which means the `siz` form her entry in STORY.md calls
  for has nowhere to appear in any language.
- **The decimal separator is the dot the code produces.** Turkish would write a
  comma, but that is a formatting job for the code rather than something a locale
  row can fix, and the game shows dots everywhere.

Everything that used to be listed here - quest text, item and location names,
skill and stance names, descriptions, the log messages, the interface labels - now
lives behind ids. `npm run check` verifies that all 1242 declared ids resolve, that
the assembled names of the 203 generated items still equal their registry keys, and
that no locale has an unknown key; `npm test` verifies that every locale keeps
`%HeroName%` intact and keeps the same `{slots}` as the reference.

## 6. Working on a translation

1. `npm run check` — see where the coverage stands.
2. Pick a whole context unit, not a row of the missing-keys list.
3. Read the English text **and** its neighbours before writing anything.
4. Write the translation, then reread it on its own without the English. If it
   reads like a translation, it is not finished.
5. `npm run check` again — an unknown key means a typo in an id.
6. `npm test` — the fallback and lookup behaviour is covered there.
7. Boot the game, switch the language in the options panel, and look at the actual
   screens you touched.
